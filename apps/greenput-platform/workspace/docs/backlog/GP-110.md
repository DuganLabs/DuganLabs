## Where this stands (2026-09-14)

Step 1 of the fix shipped in #152: `POST /api/chat/rooms/:id/sms-fallback`
answers `410 SMS_FALLBACK_REMOVED` before any config check, and
`chat.spec.ts` asserts no outbound request is made with a fully-populated
Twilio env. The Twilio credentials were added to Doppler AFTER that merge, so
the spend surface was zero when they arrived.

GP-055 is resolved — the owner chose to ship chat, and it is now reachable:
`/chat` is in the nav, Message on a customer or a job opens the room about
it, and the chat router reads the session principal correctly (it used to
read `req.session`, which nothing set). So step 2 is **unblocked and is the
remaining work**: a proper SMS fallback keyed on `recipientUserId`, resolved
server-side to a new `users.mobile_phone`, checked against the workspace and
room `:id`, under a per-workspace daily cap. Nothing in the chat UI offers
"send as SMS" — the 410 stays until step 2 lands. Step 3, the console spend
limit, is the owner's to set.

## What the user hits

Nothing — the endpoint is closed. Before #152 it answered
`503 SMS_NOT_CONFIGURED` only because Twilio was unconfigured, and the moment
real credentials existed this would have become live.

What it becomes: a signed-in user of any workspace can send arbitrary SMS text
to arbitrary phone numbers, worldwide, on the account owner's bill. That is a
metered-spend hole and an SMS relay — the kind of thing that gets a Twilio
account suspended for abuse, not just billed.

## Why it happens

`POST /api/chat/rooms/:id/sms-fallback`
(`apps/api/src/routes/chat.ts:367`) takes the destination straight off the
request body:

```ts
const body = (await req.json()) as { recipientPhone: string; message: string };
…
To: body.recipientPhone,
Body: `[Greenput] ${session.firstName}: ${body.message}`,
```

Three things are missing, and the third is the expensive one:

1. **`:id` is never read.** The room the SMS is supposedly a fallback for is
   not looked up, so the caller need not be in it — or in any room.
2. **No workspace check on the recipient.** Nothing ties `recipientPhone` to
   the caller's workspace, or to a Greenput user at all.
3. **No per-workspace or per-account cap.** The only limiter is the general
   60-a-minute-per-IP budget, which is a rate on the caller, not a ceiling on
   spend. 60 international SMS a minute per IP, from any signed-in account.

Reachability was the only thing protecting it before #152: chat was linked
from nowhere (GP-055, since shipped), so no screen called this. But the route
is mounted and authenticated, and "nothing in the UI calls it" is not a
security control.

## The fix

Ship the guard before the credential.

1. **Close the hole now.** Answer `410 Gone` unconditionally (before the Twilio
   config check), with a comment pointing here. The endpoint has no caller, so
   nothing regresses, and the spend surface drops to zero the moment this
   merges — which is what makes it safe to put a real `TWILIO_AUTH_TOKEN` in
   Doppler.
2. **Now that chat has shipped (GP-055), reinstate it properly:**
   - take `recipientUserId`, not a phone number, and resolve the number
     server-side;
   - require that user to be in the caller's workspace AND a participant in
     room `:id`;
   - **do not use `users.recovery_phone`.** That column is the account-recovery
     channel and is documented write-only from the outside, never returned in
     full by any endpoint. Chat needs its own teammate contact number — a new
     nullable `users.mobile_phone`, set by the teammate;
   - a per-workspace daily SMS counter in D1, checked before the send and
     incremented after, with a low default and a clear error past it.
3. Independently of the code, set a spend limit in the Twilio console. A cap in
   the application cannot protect against a bug in the application.

## How we will know it worked

`apps/api/src/routes/chat.spec.ts`: a POST to `/api/chat/rooms/<any>/sms-fallback`
with a fully-populated Twilio env answers 410 and `fetch` is never called — the
assertion is on the absence of the outbound request, not on the status code
alone, because the status is what a config check already returns today.

## Step 2, as shipped (2026-10-16)

- `apps/api/src/lib/sms-fallback.ts`: server-side recipient resolution
  (`recipientUserId` → `users.mobile_phone`, migration 034 — never
  `recovery_phone`), workspace + room-participation checks (room creator,
  message author, or read-receipt holder), and the per-workspace daily
  cap (50/day, counted in `sms_fallback_sends`, checked before the send
  and written after a successful one).
- The route ignores any `recipientPhone` in the body — there is no path
  from request input to the Twilio `To` field — and answers 503
  `SMS_NOT_CONFIGURED` when Twilio is unset, as the original did.
- Teammates set their own number at
  `PUT /api/workspace/users/:id/mobile-phone` (self only, E.164,
  answered masked).
- chat.spec.ts now pins the step-2 shape over the real schema: the
  happy path asserts the outbound `To` is the stored number; the
  cross-workspace, non-participant, no-number, old-body-shape, and
  cap-reached cases each assert nothing is sent.

## Notes

- Found while auditing the spend surface before the owner added Twilio
  credentials to Doppler, not by the journey audit — the endpoint is
  unreachable from every UI, so driving the product as a user cannot find it.
  Worth remembering when the next audit is scoped: "reachable" and "exposed"
  are different questions.
- `/api/auth/otp/*` is the other Twilio caller and is sound by comparison: it
  has its own 10-a-minute budget (§6.1), and `otp/send` only texts a number
  that already matches a stored `recovery_phone`, so it cannot be pointed at an
  arbitrary destination. `otp/recovery/start` does text a candidate number, but
  only for a signed-in user claiming it, under that same budget.
