## What the user hits

A developer reads a DuganLabs blog post, copies the three-line snippet it offers, and every one of them fails: two import or call functions BaseNative has never exported, and the "get started" command installs a package that does not exist on any registry. Worse, the post they are reading is not the post in the repo — a content fix merged to `main` weeks ago still is not on the site, because posts are served from a KV namespace that nothing re-seeds on deploy. So the site quietly serves whatever was hand-loaded into KV the last time someone remembered to do it, including a link to a domain that no longer resolves.

## Why it happens

Two independent causes.

**1. Nothing publishes `worker/posts/*.md` to KV.** The read path is KV-only: `worker/index.js:74` (`env.BLOG.get('posts:index', 'json')`), `:93` (``env.BLOG.get(`post:${slug}`, 'text')`` for `GET /api/posts/:slug`) and `:312` (the same read for the SSR `/blog/:slug` shell). The only writers are `POST /api/posts` (`worker/index.js:108-126`) and `worker/seed-blog.js`. `seed-blog.js` cannot run: it calls `readFileSync` from `node:fs` at `worker/seed-blog.js:6` inside what is otherwise a Worker module, and the command `BLOG_SETUP.md:73` tells you to use — `wrangler execute seed-blog.js --env production` — is not a real wrangler command (CLAUDE.md's Epic 1 section already records both facts). `worker/project.json`'s `deploy` target runs exactly one command, `pnpm exec wrangler deploy`, and `.github/workflows/deploy.yml` delegates to `DuganLabs/.github/.github/workflows/cf-worker-deploy.yml@main` with `deploy-command: "pnpm exec nx run worker:deploy"` — no KV step anywhere. Consequence: commit `d496794` repointed `worker/posts/basenative-launch.md:31` from `basenative.dev` to `basenative.com` (and `git grep basenative.dev` on `main` is now clean; `getent hosts basenative.dev` returns no record), yet `curl https://duganlabs.com/api/posts/basenative-launch` still returns two `basenative.dev` occurrences and zero `basenative.com`. Every content fix in this repo is invisible for the same reason.

**2. Three code samples name APIs that do not exist.** All three are still wrong in source and live.

- `worker/posts/ecosystem-update-q2.md:18-19`:
  `import { installComponent } from '@basenative/marketplace';` / `await installComponent('some-org/card-component');`
  `BaseNative/packages/marketplace/src/index.js` exports only `createRegistry`, `createInstaller`, `createThemeManager`, `renderPackageCard`, `packageCardStyles`. `installComponent` appears nowhere in `BaseNative/packages`. The real shape is `createInstaller({ registry, targetDir }).install(name, version)` (`BaseNative/packages/marketplace/src/installer.js:19` and `:47`), and that file imports `node:fs/promises` and `node:child_process` at `:1-3`, so it is a CLI/Node-time tool. The sample is wrong in name *and* in kind — it reads like something you can call from a browser.
- `worker/posts/ecosystem-update-q2.md:27-28`:
  `const channel = realtime.subscribe('chat:room-id');` / `channel.on('message', …)`
  There is no import line at all, and no `realtime` object or `subscribe` function anywhere in BaseNative. `BaseNative/packages/realtime/src/index.js` exports only `createSSEServer`, `sseMiddleware` (`src/sse.js:10`, `:128`), `createChannelManager` (`src/channel.js:8`) and `createWSHandler` (`src/ws.js:9`). `createChannelManager()` returns `{ createChannel, join, leave, broadcast, getMembers, deleteChannel, getChannels, removeFromAll }` (`src/channel.js:66-75`) — server-side, and `broadcast` needs a caller-supplied send function. Neither `sse.js` nor `ws.js` ships a client `EventSource`/`WebSocket` helper. This is not a rename: the client subscription API the post demos exists in no form, under a "Shipping This Week" heading dated 2026-04-20.
- `worker/posts/basenative-launch.md:34`: `npx create-basenative@latest my-app`. `registry.npmjs.org/create-basenative` returns 404. `create-basenative` exists only as a *bin* inside `@basenative/cli` (`BaseNative/packages/cli/package.json:8`), so there is no package for `npx` to fetch. Separately, `.npmrc:6` in this repo pins `@basenative:registry=https://npm.pkg.github.com/` with an auth token, so any `@basenative/*` install instruction aimed at the public needs to be verified against what is actually anonymously fetchable before it is printed.

No test guards either cause: `tests/` has no post-markdown, code-sample, or external-link assertions. The nearest thing, `tests/pages.test.mjs:118-129` (`describe('outbound links')`), only checks `pages/*.html` hrefs against the two private-repo URLs listed at `:121-124`.

## The fix

Do the samples and the publish step in one change — fixing the markdown without a publish step produces no visible improvement, which is exactly the trap that hid `d496794`.

1. **Rewrite `worker/posts/ecosystem-update-q2.md:17-20`** (the marketplace fence) to the API that exists, and say it is a Node/CLI tool so nobody tries it in a browser:
   ```javascript
   // Node / CLI — the installer shells out to your package manager.
   import { createRegistry, createInstaller } from '@basenative/marketplace';

   const registry = createRegistry({ url: 'https://registry.basenative.com' });
   const installer = createInstaller({ registry, targetDir: process.cwd() });
   await installer.install('@basenative/components');
   ```
   Confirm the registry URL you print: `BaseNative/packages/marketplace/src/registry.js:9` still defaults to `https://registry.basenative.dev`, a domain with no DNS record. If that default has not been fixed upstream, omit the `url` option from the sample rather than printing a dead host, and file the upstream default as a BaseNative ticket.
2. **Rewrite `worker/posts/ecosystem-update-q2.md:25-29`** (the realtime heading and fence) to the server-side channel API, and drop "Shipping This Week" — `@basenative/realtime` is at `0.3.1` locally, so describe what ships, not a roadmap:
   ```javascript
   import { createChannelManager } from '@basenative/realtime';

   const channels = createChannelManager();
   channels.createChannel('chat:room-id');
   channels.join('chat:room-id', clientId, (event) => send(clientId, event));
   channels.broadcast('chat:room-id', { type: 'message', text: 'hello' });
   ```
   Verify the `join`/`broadcast` argument order against `BaseNative/packages/realtime/src/channel.js` before committing — the ticket's snippet is shaped from the export list, not from a run. Do **not** invent a `realtime.subscribe` client wrapper here to make the old copy true; a client helper is a BaseNative feature request, not a blog-post fix.
3. **Fix `worker/posts/basenative-launch.md:33-35`.** Run `npm view @basenative/cli versions bin` and `npm view create-basenative version` first. If an anonymously-installable `@basenative/cli` exposes the `create-basenative` bin, print `npx --package=@basenative/cli create-basenative my-app` (the correct way to run a bin whose name differs from its package). If it does not — the likely case, given `.npmrc:6` — replace the snippet with the authenticated install plus `bn create my-app` (`BaseNative/packages/cli/src/index.js:23` registers the `create` command), and note the scoped-registry step. Either way the page must not print a command that 404s.
4. **Add `worker/scripts/publish-posts.mjs`** — a plain Node script, *not* a Worker module, which is why `seed-blog.js` failed. It should `readdir` `worker/posts/`, skip `README.md`, import `parseBlogFrontmatter` and `indexEntry` from `../blog-content.js` (already Node-safe: `worker/blog-content.js:10` imports only `@basenative/markdown`), and for each post shell out to `npx wrangler kv key put --binding BLOG --remote "post:<slug>" --path <file>`, then write the assembled index to a temp file and `npx wrangler kv key put --binding BLOG --remote posts:index --path <tmp>`. Run it with `cwd: worker` so `wrangler.toml`'s `BLOG` binding (`worker/wrangler.toml:11-13`, id `6abd29c8014f4b70add446dc20cd9c06`) resolves. Reuse `indexEntry` rather than rebuilding entries — `worker/blog-content.js`'s header records that a second implementation already got tags wrong once.
5. **Delete `worker/seed-blog.js`** and replace the `BLOG_SETUP.md:66-75` "Seed the KV Store" section with the new script's command. Leaving a broken seeder next to a working one guarantees someone runs the broken one.
6. **Chain the publish into deploy** by turning `worker/project.json`'s `deploy` target into an `nx:run-commands` `commands: [...]` array — `pnpm exec wrangler deploy` then `node scripts/publish-posts.mjs` — both with `cwd: worker`. Do it here rather than adding a job to `.github/workflows/deploy.yml`: the deploy is a thin caller into `DuganLabs/.github/.github/workflows/cf-worker-deploy.yml@main` which accepts a single `deploy-command`, so the Cloudflare credentials only exist inside that job. Chaining in the nx target needs no new secret plumbing. Publishing must run after `wrangler deploy`, so that a KV write failure does not leave a deployed worker reading a half-written index.
7. **Chose wrangler KV over `POST /api/posts`** for step 4 because `worker/index.js:108` has no authentication — building the deploy pipeline on that endpoint would make an unauthenticated public write path load-bearing. The KV route uses the `CLOUDFLARE_API_TOKEN` CI already has and works even when the worker is broken.

## How we will know it worked

- **New test, `tests/posts.test.mjs`** (picked up automatically — `package.json`'s `test` script is `node --test "tests/**/*.test.mjs"`), with two cases:
  1. *Code samples name only real exports.* Parse every ```javascript fence in `worker/posts/*.md`, collect every `from '@basenative/<pkg>'` specifier and its named imports, and assert each is present in a checked-in `worker/posts/api-manifest.json` mapping package → exported names. Seed the manifest from `BaseNative/packages/*/src/index.js`. Also assert no fence contains a bare identifier from a `FORBIDDEN` list — `installComponent`, `realtime.subscribe` — so the exact two regressions cannot come back. This test fails on current `main` (both symbols are present at `ecosystem-update-q2.md:18,19,27`) and passes after steps 1-2. BaseNative is a sibling checkout, not a dependency of this repo, so the manifest is hand-maintained by design; the test's job is to fail when a post drifts from it.
  2. *Deploy publishes posts.* Read `worker/project.json` and assert the `deploy` target's commands include `publish-posts`. Fails today (the target is a single `wrangler deploy`), passes after step 6. This is the only offline guard against the staleness class.
- **By hand, after the next deploy to `main`** — no test can reach the live KV:
  ```
  curl -s https://duganlabs.com/api/posts/basenative-launch | grep -c basenative.dev   # expect 0
  curl -s https://duganlabs.com/api/posts/basenative-launch | grep -c basenative.com   # expect >=1
  curl -s https://duganlabs.com/api/posts/ecosystem-update-q2 | grep -cE 'installComponent|realtime\.subscribe'  # expect 0
  ```
  All three currently give the opposite answer (2, 0, 3). Also load `https://duganlabs.com/blog/ecosystem-update-q2` in a browser and read the two fences — the SSR path at `worker/index.js:312` is a separate read of the same key, and it is what a human actually sees.

## Notes

- **One root cause, two symptoms.** The dead `basenative.dev` link was "fixed" in `d496794` and the fix is still not live. Any future ticket that edits `worker/posts/*.md` is a no-op for readers until step 4/6 of this ticket lands. If you are triaging another content ticket and it is blocked on publishing, it depends on this one.
- **Why not just re-run a seeder by hand.** That is the current process and it is what produced this bug; the hand step has been skipped for at least one merged fix. The ticket is deliberately sized to include the automation.
- **CLAUDE.md constraints that shape the fix:** "No build step" (Constitution 1) — `publish-posts.mjs` is a deploy-time Node script, not a build of the site, same category as the `seed-blog.js` it replaces; nothing about the served pages changes shape. Constitution 4 already acknowledges the two KV namespaces, so no doc edit is needed there. Commit messages need `Co-Authored-By: Claude Opus 4.6 <noreply@anthropic.com>` per the Commit Convention section.
- **Do not "fix" the samples by adding the missing APIs to BaseNative.** `installComponent` and a client `subscribe` are upstream design decisions in a different repo; this ticket's job is to stop `duganlabs.com` publishing code that cannot run. If you want the client subscription helper, open it against BaseNative separately.
- **Published versions lag local.** `@basenative/marketplace` is `0.2.2` and `@basenative/realtime` `0.3.1` in the local checkout, against `0.2.0` on npmjs, and `@basenative/cli` is `0.5.0` locally. The published code is *less* likely to have the exports a sample names, so validate any snippet against the version a reader can actually install, not against the working tree.
